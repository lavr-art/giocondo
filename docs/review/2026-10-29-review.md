# Ревью giocondo (vpnctl) — 2026-10-29

Охват: весь репозиторий (~19 тыс. строк Go, 20 пакетов), состояние рабочей копии без коммитов.
У каждой находки есть `file:line` и сценарий отказа. В этом проходе ничего не исправлялось.

## Итог

Основа здоровая: граница агента закреплена тестом, mTLS сверяет CN с базой,
в CSP нет inline-кода, API-токены хранятся хешами, секреты сравниваются за постоянное время, у генераторов
есть golden-тесты, покрытие 35–89 %. Сервис — не «куча мусорного кода».

Слабые места сосредоточены в трёх областях:

1. **Учёт и согласованность состояния**: дедупликация трафика только в памяти, потерянное обновление WG-ключей,
   неудачное первое применение отображается как успех.
2. **Безопасность на границах**: токен `monitor` видит ссылки подписок, лимитер входа за
   reverse proxy блокирует всех, ключ хоста SSH не запоминается, релизы собираются Go 1.26.0
   с известными уязвимостями stdlib.
3. **Сетевая подсистема (задача 7)** написана в другом стиле и качестве: на ней все
   замечания линтера, магические строки статусов, мёртвый код и фоновые операции, которых не ждут при остановке.

## Высокий приоритет

### H1. Релизы собираются Go 1.26.0 с известными уязвимостями
В `go.mod:3` указано `go 1.26.0` без `toolchain`; `.github/workflows/{ci,release}.yml` берут версию
через `go-version-file: go.mod`, поэтому ставится ровно 1.26.0. govulncheck находит 36 достижимых
уязвимостей stdlib, исправленных в 1.26.1–1.26.9 (паники x509 на gRPC/HTTP-сервере, net/http).
**Исправление**: `toolchain go1.26.<latest>` в go.mod (или `go-version: stable` в CI) плюс
шаг `govulncheck ./...` в CI; обновить x/net до ≥ v0.62.0. Объём: S.

### H2. Токен `monitor` получает ссылки подписок всех пользователей
`internal/api/api.go:39-41` (`GET /api/users`, `/api/users/{id}` со scope monitor) →
`internal/admin/admin.go:114` `SubscriptionURL = SubURL + "/sub/" + Token`.
Ссылка подписки — это UUID и приватный ключ WireGuard. Токен только для чтения для дашборда или
мониторинга может подключиться как любой пользователь. **Исправление**: отдавать `subscription_url` только для scope admin
(или отдельным admin-маршрутом). Меняет контракт API, поэтому решение за пользователем.

### H3. Трафик удваивается после перезапуска панели
`internal/nodehub/hub.go:47,512-549`: дедупликация `instance_id/seq` живёт только в `Hub.lastSeqs`
(в памяти); seq в базе нет (`rg seq internal/store` пуст).
Сценарий: панель записывает пакет seq=N и отправляет ack → панель перезапускается (или ack теряется при
разрыве) → агент переподключается и отправляет тот же пакет seq=N (`internal/agent/agent.go:190`) →
новый процесс записывает его второй раз. Пользователь упирается в лимит раньше времени. Нарушает инвариант
CLAUDE.md «не удваивать трафик при переподключении».
**Исправление**: таблица `node_stats_seq(node_id, instance_id, seq)`, проверяемая и записываемая в той же
транзакции, что и `AddTraffic`. Новая миграция плюс тест перезапуска хаба. Объём: M.

### H4. Неудачное первое применение конфига показывается как успешное
`internal/agent/apply.go:81-83`: при `!hadOld` сломанный конфиг остаётся в `config.json`.
Затем `handle` отправляет `ApplyResult{ok:false}`, за ним `health()` с `CurrentHash()` = хеш
сломанного конфига (`agent.go:255,274`) → хаб в `hub.go:367-369` видит новый хеш и вызывает
`applied(hash, "")`: `apply_error` очищается, узел не dirty, хотя sing-box не запущен.
Нарушает «ошибка не должна сообщаться как успех». **Исправление**: при неудаче без `.prev` переносить
конфиг в `config.json.failed` (CurrentHash → ""); тест в `apply_test.go` плюс тест хаба на Health. Объём: S.

### H5. Потерянные обновления пользователя: WG-ключи и правки админа затирают друг друга
`internal/store/users.go:114-118`: `UpdateUser` пишет всю строку, включая `wg_*`.
Read-modify-write без транзакции есть в двух местах:
`internal/nodehub/wg.go:19-59` (`EnsureWGPeers`, вызывается из Sync каждые 30 с и по Kick)
и `internal/admin/admin.go:248+` (`UpdateUser`).
Сценарий A: админ прочитал пользователя → хаб выдал ключи → `UpdateUser` админа
пишет `wg_*=NULL` → следующая сверка генерирует **новые** ключи и адрес → WireGuard у клиента перестаёт
работать. Сценарий B: хаб прочитал список → админ изменил лимит/enabled →
хаб записывает устаревшие поля. **Исправление**: точечный `SetUserWG(id, peer) WHERE wg_public_key=''`
и `UpdateUser` без WG-колонок. Объём: S–M.

### H6. Лимитер входа за reverse proxy блокирует всех
`internal/web/auth.go:92-98,web.go:270`: ключ лимитера — `r.RemoteAddr`; по
документации (`docs/release.md:64`, `panel.env`) панель слушает 127.0.0.1 за прокси, поэтому у всех
один и тот же IP. 10 неверных паролей от кого угодно → админ не может войти 10 минут, атака повторяема.
`X-Forwarded-For` нигде не обрабатывается. **Исправление**: env `PANEL_TRUSTED_PROXIES` и
разбор XFF только от доверенных адресов (решение за пользователем). Объём: S.

### H7. CI красный: lint v2.15.0 падает
21 замечание: `healthcheck/check.go:124,139,187,257`, `healthcheck/remote.go:69,90-118`,
`provision/state.go:17,27,34,67`, `store/network.go:66,172,246`, `store/network_test.go`,
`admin/watch.go:95` (unused). Локальный `make lint` вообще не запускается из-за старого
golangci-lint. **Исправление**: устранить замечания; Makefile должен запускать закреплённую
версию (`go run …/golangci-lint/v2/cmd/golangci-lint@v2.15.0`). Объём: S.

## Средний приоритет

### M1. Остановка панели не ждёт фоновых задач
`cmd/panel/main.go:179,218-220,237-242`: `hooks.Run`, `Watch`, `CheckNodes`, `Reconcile`,
операции в `rotate.go:93`, `resume.go:57`, `provision/jobs.go:83` не ожидаются; `defer st.Close()`
закрывает базу, пока они пишут. Операция смены IP получает отменённый ctx → сохраняется как
`failed` (если успевает до Close) → `RecoverNetworkOperations` (`rotate.go:289`) её не
восстанавливает, хотя DNS мог уже переключиться. **Исправление**: `sync.WaitGroup` в
`admin.Service` для фоновых операций, порядок остановки HTTP → gRPC → фон → база;
при отмене из-за остановки сохранять статус `running` для восстановления. Объём: M.

### M2. Сбой DNS API при старте не даёт панели запуститься
`cmd/panel/main.go:170-172` + `admin/rotate.go:296-313`: если есть операция `running`,
а Cloudflare недоступен или DNS неоднозначен, `run()` возвращает ошибку → systemd перезапускает
панель по кругу; подписки и Sync недоступны для всех узлов из-за одного узла.
**Исправление**: логировать восстановление и повторять его в фоне, держа узел заблокированным. Объём: S.

### M3. Ключ хоста SSH проверяется, только если отпечаток введён вручную
`internal/provision/ssh.go:117-123`: при пустом `HostKeySHA256` принимается любой ключ;
полученный отпечаток только логируется (`admin/provision.go:104,107`) и нигде не
сохраняется. Повторные операции (ротация, откат, `web/network.go:33,38,60`) с паролем root
доверяют любому серверу → MITM получает пароль. **Исправление**: сохранять отпечаток в
`node_installations` при первой установке и требовать совпадения дальше (настоящий TOFU). Объём: M.

### M4. Сессии нельзя отозвать
`internal/web/auth.go:36-77`: подпись не зависит от пароля, сервер не хранит сессии.
Logout только удаляет локальную cookie; украденная cookie живёт 7 дней; смена
`PANEL_ADMIN_PASSWORD` не сбрасывает сессии. **Исправление**: ключ подписи =
HMAC(secret, sha256(password)), тогда смена пароля отзывает всё. Объём: S.

### M5. Переименование пользователя теряет трафик и перезапускает ядро
Счётчики sing-box и WG outbound'ы названы по имени пользователя (`agent/stats.go:22-38`),
а панель сопоставляет по имени (`nodehub/hub.go:523-533`). После `UpdateUser{name}` и до
применения нового конфига (до 30 с throttle) пакеты приходят под старым именем → «traffic for
unknown user», трафик теряется. **Исправление**: использовать в конфиге узла стабильный идентификатор (`u<id>`), а имя
оставить только в панели. Меняет формат конфига и golden-файлы, поэтому решение за пользователем. Объём: M.

### M6. Ошибка resume/rollback сохраняется без очистки
`internal/admin/resume.go:159` `o.Error = err.Error()`, тогда как `rotate.go` использует
`healthcheck.SafeError`. Сырой вывод SSH/подпроцессов попадает в базу и UI. Объём: XS.

## Низкий приоритет

- **L1** `agent/apply.go:53,73,84`: нет fsync перед rename; откат пишет `config.json` через
  `os.WriteFile` (не атомарно). Пропадание питания может оставить пустой конфиг. Атомарно:
  rename `.prev` → `config.json`.
- **L2** `nodehub/hub.go:227-263`: `NetworkConfig` отправляется при каждом push (30 с + Kick),
  и агент каждый раз запускает `iptables-restore`. Отправлять при смене хеша.
- **L3** Нет очистки истории: `network_operations` (JSON payload с растущим `Log`, `ListNetworkOperations`
  без лимита в `nodeView`), `traffic` и `node_probes` растут бесконечно.
- **L4** `agent.go`: `pending` трафик в памяти теряется при перезапуске агента (до минуты);
  допустимо, но стоит задокументировать.
- **L5** Проверить на реальном узле: `vpnctl-agent.service` с `ProtectSystem=strict` и
  `iptables -w` (lock в `/run`). На Docker-стенде прошло, но может упасть с iptables-legacy.

## Архитектура и структура

- **A1. Выдача WG-ключей — побочный эффект сборки конфига.** Реализована в трёх местах:
  `nodehub/wg.go` (вызывается из `Hub.buildConfig` в Sync), `admin/admin.go:231`, `admin/health.go:19-75`.
  Синхронизация — глобальный `store.WGAllocationMu` (`store/network.go:13`). Предложение: выделять
  в `admin` при создании пользователя или WG-inbound, в одной функции; хаб только читает. Это также
  закрывает H5.
- **A2. Веб-интерфейс обходит admin**: `web/web.go:424-435` (`userWG`) читает Store и собирает WG-конфиг.
  Перенести в `admin.WireGuardConfig(userID, nodeID)`; при желании добавить API-маршрут.
- **A3. Зависимости**: `nodehub` импортирует `internal/agent` ради `agent.Hash`. Перенести
  `Hash` в `internal/nodeapi`, общий контракт обеих сторон.
- **A4. Конфигурация панели разбросана** по `cmd/panel/main.go:103-230` (`os.Getenv` в 20+ местах),
  значения по умолчанию дублируются (`PANEL_GRPC_LISTEN` в `:266,307`; `PANEL_PKI_DIR` в `:124,271`).
  Вынести `type config struct` + `loadConfig(getenv)` с табличным тестом. `run()` станет
  читаемым, а валидация будет в одном месте.
- **A5. Привести сетевую подсистему к стилю остального кода**: `store/network.go`,
  `admin/{network,rotate,resume,health}.go`, `api/network.go`, `dns/`, `healthcheck/`:
  функции без пустых строк между ними, безымянные параметры в интерфейсе `Store`
  (`store.go`), магические строки статусов (`"running"`, `"retired"`, `"candidate"`,
  `"switched"`), которым нужны типизированные константы как `NodeStatus`.
- **A6. API**: `/api/jobs/{id}` (provisioning, в памяти) и `/api/jobs/{id}/{action}`
  (сетевые операции, в базе) — две разные сущности в одном пространстве имён. Переименовать
  второе в `/api/operations/{id}/{action}` (меняет контракт, поэтому решение за пользователем).
- **A7. Дубликаты**: `admin/nodes.go:465 shellQuote` ≡ `provision/ssh.go:213 quote`.
- **A8. Интерфейс `store.Store` содержит 58 методов** и одну реализацию. Не дробить его ради дробления;
  достаточно убрать то, что уходит в A1, и назвать параметры.

## Чего не хватает сервису

По убыванию ценности (каждый пункт — отдельный мини-план по решению пользователя):

1. **Первый коммит**: без истории нет ревью диффа, worktree и релиза.
2. **Backup/restore**: `vpnctl-panel backup <dir>` (`VACUUM INTO` + PKI). Панель —
   единственный источник истины; потерять её сейчас значит потерять всё.
3. **Health-эндпоинт панели** (`/healthz` на admin-сервере) для мониторинга доступности и проверок после деплоя.
4. **`.golangci.yml`** с `errorlint`, `bodyclose`, `noctx`, `gosec` (как минимум) плюс
   `govulncheck` и `go test -race` в CI.
5. **Очистка** истории трафика, проб и операций (L3).
6. **README/документация оператора**: установка панели и узла, обновление, восстановление
   узла, список env-переменных. Сейчас README пуст.
7. Журнал аудита действий администратора: опционально; для личного использования может подождать.
